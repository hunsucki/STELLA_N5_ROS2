# 후진 중 벽 재확인과 제자리 정렬 복구 — 2026-09-18 16:56

이번 실행은 180° 회전(목표 오차 -0.16°)과 후면 정렬(-0.96°)을 완료하고 후진했다. 약 7초 뒤 벽 후보 -4.34°, IMU 누적 +9.22°, 휠 약 -0.5°에서 중단됐다. 평면 잔차는 IMU +5.36°, odom +4.51°, 휠 -4.32°로 모든 기존 기준을 벗어났다. 이전 wheel guard는 -3.69° 후보에서도 직선 후진을 허용했고, 이후 평면을 거부하자 누적 IMU 8° 제한이 정지 재획득 절차보다 먼저 실행됐다.

확인된 결함은 (1) 벽 오차가 커져도 wheel guard에서 각도를 맞추지 않는 점, (2) 최초 평면 기준과 달라진 벽을 정지 후에도 복구할 수 없는 점, (3) IMU 누적값이 재획득 대기를 즉시 종료하는 점이다. IMU 바이어스, 차체 미끄러짐, RANSAC 대상 변화 중 물리 원인은 텍스트 로그만으로 확정할 수 없다.

현재 복구 순서:

1. 평면 후보 오차가 3° 이상이면 wheel guard 직선 후진을 금지하고 정지한다.
2. 3초 재획득 구간에서 IMU/odom 각속도가 정지 조건을 만족하고 휠 변화가 0.5° 이내인지 확인한다.
3. 유효 후보의 inlier 비율 85% 이상, 길이 0.30 m 이상, 각도 8° 이내를 요구한다. 서로 다른 5개 스캔의 전체 각도 폭이 1° 이내여야 하며 최소 0.4초 기다린다.
4. 이 조건을 만족할 때 한 번만 새 평면 기준과 IMU heading 기준을 확정한다. 선속도 0으로 제자리 보정하고, 기존 1°/정지/연속 스캔 완료 조건을 만족해야 후진을 재개한다.
5. 주행 내 반복 기준 재설정은 허용하지 않는다. 휠 누적 제한, 거리 보호, 시간 제한은 계속 검사한다.

실제 backup_with_lidar 루프에 로그의 각도 불일치와 정지 후 고품질 벽 관측을 입력하는 시험을 추가했다. 정상 회전 응답은 벽 오차를 줄인 뒤 거리 목표에 도달하고, 반대 회전과 무응답에서는 후진 재개가 차단된다. 낮은 품질의 지속 불일치는 정지 상태에서 재획득 제한을 소진하며, 일시적 불일치는 정상 관측이 돌아오면 회복한다. 도킹 패키지 232개 테스트가 모두 통과했고 빌드 및 설치 모듈 확인을 완료했다. 이는 제어 루프 모의시험이며 원시 scan 재생 또는 실물 성공 검증은 아니다.

# 최신 실패 분석과 정렬 outlier 합의 수정 — 2026-09-18 16:45

이번 실행은 태그 접근과 정밀 보정을 완료했고 절대 odom 180° 회전도 `target_error=0.13°`로 정확히 끝냈다. 실패 위치는 후진 단계가 아니라 그 직전의 정지 LiDAR 평면 정렬이다.

```text
rear plane acquired:            -2.84deg
normal fits while converging:   about -0.8..+1.6deg
isolated alternate candidates:  about -4.1deg
tracking residuals:             -5.23, +5.24, -5.49, -5.26, -5.73deg
final convergence:              +1.42 -> +1.33 -> +0.97 -> +0.18 -> +0.55deg
failure:                        12s LiDAR alignment timeout
```

회전 방향과 회전량은 정상이다. 정렬 누적 회전도 6.89°로 18° 안전 예산보다 충분히 작았다. 문제는 RANSAC 후보가 5° soft tracking limit를 한 번만 넘어도 코드가 정상적으로 추적하던 평면, 획득 3스캔, 완료 5스캔 상태를 모두 지운다는 점이었다. 로그에서는 이 outlier가 연속되지 않았고 그 사이마다 길이 약 0.53 m, inlier 약 104~112개의 정상 후면 패널 후보가 돌아왔다. 마지막에는 이미 1° 안으로 들어왔지만 앞선 초기화로 완료 스캔을 모으기 전에 timeout이 됐다.

5° 한계를 넓히면 실제로 다른 구조를 선택한 후보도 조향에 사용할 수 있다. 현재 수정은 각도 경계를 유지하면서 시간 합의를 추가한다.

1. 5~12° 불일치 첫 스캔에서는 즉시 정지하고 그 후보를 제어에 사용하지 않는다.
2. 기존 추적 평면은 유지하며 다음 고유 스캔을 확인한다.
3. 다음 스캔이 기존 평면과 일치하면 outlier 횟수를 0으로 되돌린다.
4. 5~12° 불일치가 2회 연속될 때만 기존 평면을 폐기하고 정지 상태에서 3스캔을 재획득한다.
5. 12° 초과는 다른 구조 전환으로 보고 기존과 같이 즉시 실패한다.
6. 보호 정지 뒤 최종 완료 5스캔을 확보할 수 있도록 전체 정렬 제한을 12초에서 18초로 늘린다. 누적 회전의 18° 기본 예산과 30° hard limit는 유지한다.

첨부 로그의 다섯 outlier 잔차를 순서대로 재현해 각 단일 outlier가 재획득을 만들지 않는지, 두 번 연속된 soft outlier는 재획득하는지, hard outlier는 즉시 중단되는지 회귀시험으로 고정했다. 실물 재시험에서는 `Ignoring isolated inconsistent ... retaining` 다음 정상 `LiDAR align` 로그가 이어지고, `LiDAR plane alignment complete` 뒤 후진이 시작되는지 확인해야 한다.

# 이전 실패 분석과 엔코더 heading guard 추가 — 2026-09-18 16:32

이번 실행은 태그 접근, 정밀 보정, 절대 odom 180° 회전과 정지 LiDAR 평면 정렬까지 모두 완료했다. 정렬 종료 오차는 `0.76°`였고 후진도 정상적으로 시작됐다. 최초 실패는 2.1 cm 이동 뒤의 후진 평면 합의 판정이다.

```text
initial plane error:       about +0.7deg
later candidate:           +3.41deg
IMU / odom yaw drift:      about +2.1deg
encoder-only yaw drift:    +0.13deg
IMU / odom residual:       about +5.0deg
wheel residual:            +2.73..+2.99deg
failure: motion_inconsistent for 3 seconds
```

IMU와 IMU 보정 odom은 함께 바뀌었고 엔코더 전용 yaw는 로봇이 거의 직진했음을 나타냈다. 그러나 RANSAC 후보 자체도 후진 이동에 따라 약 2.7° 바뀌어 LiDAR-휠 잔차가 기존 2° 한계를 넘었다. 정지 뒤 후보는 `3.41 → 3.19 → 3.14°`로 안정됐지만, 코드는 후진 시작 시점의 평면 기준만 허용했기 때문에 같은 `motion_inconsistent` 상태를 반복하고 재획득 제한을 소진했다. 거리 목표와 180° 회전은 이번 실패의 원인이 아니다.

2° 정상 합의 한도를 단순히 4°로 넓히면 의심스러운 LiDAR 평면이 조향 권한을 얻어 로봇을 잘못 회전시킬 수 있다. 대신 제한된 **엔코더 heading guard**를 추가했다.

1. LiDAR가 IMU 계열 또는 엔코더 그룹 중 하나와 2° 이내에서 일치하면 기존 LiDAR 제어를 유지한다.
2. 두 그룹 모두와 모순되지만 LiDAR-휠 잔차가 4° 이내이면 로봇을 먼저 정지한다.
3. 같은 후보가 고유 스캔 3개에서 안정돼야 `wheel_guard`로 전환한다.
4. 이 상태에서는 의심스러운 LiDAR 각도로 조향하지 않는다. 엔코더 시작 yaw만 유지하며 거리 기반 후진을 재개한다.
5. LiDAR-휠 잔차가 4°를 넘거나 휠 yaw가 오래됐거나 시작 대비 휠 drift가 8°에 도달하면 기존처럼 정지·실패한다.

첨부 로그의 `candidate=3.40°`, IMU/odom `2.10°`, wheel `0.13°` 조건을 실제 `backup_with_lidar()` 루프에서 재현했다. 수정된 루프는 잠시 정지해 3개 스캔을 확인한 뒤 각속도 0으로 직선 후진을 재개하고 최종 거리 범위에서 성공한다. 4.01° 잔차와 8° 휠 drift는 guard 진입을 거부하는 회귀 시험으로 고정했다. `docking` 225개 테스트와 워크스페이스 누적 269개 테스트가 오류 0, 실패 0, 1개 skip으로 끝났고 패키지 빌드도 성공했다. 실물 재시험 전까지 이 결과는 로그 재현 시험 기준이다.

# 최신 실패 분석과 LiDAR 재획득 예산 수정 — 2026-09-15 16:16

이번 실행에서 앞선 태그 보정 수정은 실물에서 정상 동작했다. 목표점 방향 정렬, 위치 이동, 최종 yaw 정렬이 순서대로 완료됐고, 태그 오차는 `x=0.038m, y=0.023m, yaw=-1.92°`로 수렴했다. 이어진 절대 odom 180° 회전도 목표 오차 0.25°로 완료됐다.

후진은 시작되지 않았다. 최초 실패는 후진 직전의 LiDAR 평면 미세 정렬이었다.

```text
rear plane acquired: error=11.44deg
soft inconsistency: tracking_residual=5.15deg
rear plane reacquired: error=14.96deg
error convergence: 14.88 -> 11.49 -> 6.81 -> 4.32deg
failure: rotation 18.02deg >= fixed limit 18.00deg
```

첫 평면은 회전 중 일관성 검사를 통과하지 못해 코드가 정지하고 폐기했다. 재획득한 평면은 더 많은 inlier와 긴 지지를 가졌고, 이후 오차가 연속으로 감소했으므로 평면과 회전 방향은 정상이다. 문제는 폐기된 첫 평면에 사용한 약 3°와 새 평면의 14.96° 보정을 하나의 고정 18° 예산에 넣은 것이다. 정렬은 거의 끝났지만 남은 약 1~2°와 정지 안정화 전에 0.02° 차이로 중단됐다.

기본 회전 예산 18°는 유지한다. soft 불일치 또는 정지 상태의 재획득이 발생하면 다음 식으로 예산을 갱신한다.

```text
new_budget = min(30deg,
                 max(18deg, cumulative_rotation + abs(new_error) + 3deg))
```

회전량은 시작점과 현재점의 단순 차이가 아니라 고유 odom마다 이동한 yaw의 절댓값을 누적해 왕복 회전도 빠짐없이 센다. 이번 로그를 대입하면 재획득 뒤 예산은 약 20.96°가 되어 남은 정렬과 정지 확인을 수행할 수 있다. 반복 재획득이 계속되더라도 누적 30° hard limit와 12초 timeout은 유지된다. 진행 로그에 `rotation=current/budget`을 추가했다.

## 확인한 코드 결함과 수정

### 1. 설정한 20Hz가 실제 명령 주기를 제한하지 않음

기존 보정·회전·후진·LiDAR 정렬 루프는 `rclpy.spin_once(timeout_sec=0.05)`를 주기 대기처럼 사용했다. 이 함수는 콜백 하나를 처리하면 즉시 돌아온다. IMU·odom·TF·LiDAR 콜백이 계속 준비돼 있으면, 모터 명령도 센서 콜백 속도로 발행될 수 있다. 모터 드라이버는 `/cmd_vel` 콜백마다 즉시 serial write를 실행하므로 불필요한 부하를 준다. **실제 정체의 단독 원인이 이것이라고 단정하지는 않는다.**

`control.spin_for()`가 단조 시간 기준으로 한 주기 동안 콜백을 계속 처리하도록 수정했다. busy executor에서도 명령은 20Hz 이하이며, 센서 처리와 중단 신호 확인을 계속한다. 정지 명령 사이의 간격도 같은 방식으로 보장한다.

### 2. 정밀 회전의 무응답을 감지·복구하지 못함

기존 최대 회전 명령은 항상 0.08rad/s였고, 실제 yaw 응답이 사라져도 timeout까지 같은 명령을 보냈다. 새 `PrecisionYawController`는 목표 오차가 줄어드는지와 gyro·휠 각속도를 함께 검사한다.

- 정상 정밀 회전 상한: 0.08rad/s 유지.
- 1초간 유의한 진전이 없고 **fresh gyro와 휠 측정 모두 정지 상태**일 때만 회전 명령을 점진적으로 늘린다.
- 복구 상한: **0.15rad/s**, 기존 180° 회전의 설정 속도와 같음. 가속도는 0.3rad/s² 이하.
- 제한된 복구에도 4초간 진전이 없으면 정지하고 실패 원인을 기록한다.
- 센서는 회전 중인데 목표 오차가 줄지 않는 경우에는 증속하지 않고 2초 후 정지한다. gyro가 오래된 경우에도 복구 증속을 허용하지 않는다.
- 최종 yaw 보정 중 위치 오차가 경계에서 흔들려도 바로 직진으로 전환하지 않는다. 회전을 마친 뒤 위치를 재평가한다. 성공 판정에는 원래 위치·yaw 허용치와 정지 조건을 모두 적용한다.

보정 로그에 실제 각속도, 휠 각속도, 복구 명령 하한을 추가했다. 0.18m 이동·시작 대비 30° 회전 한계와 45초 전체 보정 한계는 유지한다. 이는 저속 무응답에 대한 제한된 대응이며, 충돌·기계 고장·센서 오류를 억지로 통과시키는 절차가 아니다.

### 3. 후진 중 유효 평면이 사라져도 계속 이동

기존 코드는 평면이 거부되면 조향만 0으로 바꾸고 후진을 계속했다. 이제 유효 평면 재검출까지 **linear/angular를 모두 0**으로 한다. 서로 다른 안정 스캔이 확보되면 재개하고, 2초 동안 복구되지 않으면 종료한다. 시작 시에도 평면 안정화 전에는 후진하지 않는다. 거부된 평면의 각도·inlier 수·길이를 로그로 남긴다. 기존 drift·거리·센서 유효성 제한은 그대로 적용한다.

### 4. 종료 신호와 ROS shutdown 순서 충돌

helper의 자체 신호 처리기와 `rclpy.init()`의 기본 신호 처리가 중복됐다. helper에서는 `SignalHandlerOptions.NO`로 초기화하여 자체 처리기가 중단을 요청하고, ROS가 살아 있는 상태에서 정지 명령과 자식 프로세스 정리를 완료한 뒤 context를 종료한다.

# 즉시 도킹 실패 원인과 수정 — 2026-09-09

도킹 액션 서버 이름 충돌이 즉시 실패의 원인이었다. 설치된 영상 보정 노드의 종료 crash도 별도로 재현해 처리했다. 실행 명령은 그대로 `ros2 run docking dock_turn_backup`이다.

## 로그와 실행 환경에서 확인한 내용

| 순서 | 로그 | 의미 |
|---|---|---|
| 1 | `Detected dock pose is available`, `Successful initial dock detection` | 태그 인식과 odom·LiDAR 준비는 통과 |
| 2 | `Ignoring unexpected goal response ... more than one action server` | 하나의 요청에 예상 밖 액션 응답 도착 |
| 3 | `status=0, error_code=0, error_msg=""` | 정상 성공/실패 결과가 아닌 `STATUS_UNKNOWN` 수신 |
| 4 | `Requested to deactivate server but goal is still executing` | 클라이언트는 실패했지만 관리 서버는 목표를 실행하던 중 |
| 5 | `Lost detection`, `component_container ... exit code -11` | 실패 후 정리 과정의 추가 오류 |

실패 실행이 끝나고 이 패키지의 관리 프로세스가 없는 상태에서도, ROS graph에 기존 `/docking_server`의 `/dock_robot`, `/undock_robot` 액션과 lifecycle 서비스가 남아 있음을 직접 확인했다. 기존 `ManagedStack.start()`는 이를 고려하지 않고 같은 이름의 서버를 추가로 실행했다. 같은 액션 이름의 서버가 여러 개면 목표 수락 응답과 결과 응답이 서로 다른 서버에서 도착할 수 있다.

`STATUS_UNKNOWN`은 결과를 요청받은 서버가 해당 goal ID를 모를 때 사용하는 상태다. 응답을 성공으로 간주하거나 단순 재시도하면 실행 중인 다른 목표가 남을 수 있으므로, 통신 대상을 분리하는 방식으로 수정했다. [ROS 2 액션 서버 구현](https://github.com/ros2/rclpy/blob/jazzy/rclpy/rclpy/action/server.py)

## 반영한 변경

1. **관리 서버마다 고유 namespace 사용.** `/stella_docking_<ID>/docking_server`와 그 아래의 도킹 액션, 검출 pose, 정밀 목표 pose를 사용한다. lifecycle 관리와 ActionClient도 같은 전용 경로를 사용한다. 기존 서버의 lifecycle을 변경하거나 프로세스를 종료하지 않는다.
2. **설정 보존.** 원본 YAML의 `docking_server` 또는 `/docking_server` 블록을 전용 서버 이름에 맞춰 임시 YAML에 옮긴다. wildcard 설정과 보정값은 유지하고, 종료 후 해당 임시 파일을 정리한다. `cmd_vel`, TF, 배터리, costmap, navigation 입력은 로봇의 기존 경로에 연결한다.
3. **목표 전송 전 중복 검사.** 액션의 `send_goal`, `get_result`, `cancel_goal` 서버 수가 각각 정확히 1개인지 검사한다. lifecycle 서비스 중복도 거부한다. accepted goal에 `STATUS_UNKNOWN`이 오면 원인을 명시하고 해당 goal 취소를 요청한다.
4. **영상 보정 노드 교체.** 설치된 `image_proc`은 shared container뿐 아니라 standalone 프로세스에서도 종료 시 crash 또는 지연을 보였다. 별도 `docking/image_rectifier`는 `message_filters`로 동일 시각 image/camera info를 결합하고, `image_geometry`의 보정 행렬과 OpenCV map/remap을 사용한다. 보정 map을 재사용하고 원본 촬영 시각을 유지한다. 출력 CameraInfo는 보정 영상의 P/K와 ROI·binning 조정을 반영한다.
5. **종료 검사 보완.** `ros2 launch`에는 부모 프로세스에만 SIGINT를 보내 자식에게 신호가 중복 전달되는 것을 피한다. `ros2 run` wrapper는 기존처럼 프로세스 그룹에 신호를 보낸다. 인식 통합 검증은 자식 crash와 비정상 종료도 실패 처리한다. 이전 검증은 영상·pose 전달만 확인하여 종료 crash를 놓칠 수 있었다.

- 실제 Nav2 통합 시험: DDS domain 219에 가상의 기존 `/dock_robot` 서버와 실제 `opennav_docking` 관리 서버를 함께 실행했다. 관리 서버의 목표·결과 교환이 성공했고, 기존 서버에는 목표가 전달되지 않았다. 로봇 위치는 합성 TF이며 실물 주행 단계는 실행하지 않았다.
- 보정값 확인: 실제 관리 서버에서 `controller_frequency=10.0`, `external_detection_translation_x=-0.95`를 읽어 YAML이 올바른 namespace에 적용됐음을 확인했다.
- 중복 서버 시험: 동일한 노드 이름으로 `/dock_robot` 액션을 2개 실행해도 `(2, 2, 2)` 중복을 검출하고 목표를 보내지 않았다.
- 인식·종료 시험: DDS domain 217에서 왜곡 보정, 태그 검출, 원본 시각 유지, 영상 중단 후 과거 pose 재발행 방지, 두 인식 프로세스의 정상 종료를 확인했다.
- 실제 카메라를 대상으로 한 읽기 전용 확인에서는 15초 동안 동기화된 image/camera info 쌍을 수신하지 못했다. 따라서 실물 카메라에서의 처리 속도·영상 품질 확인은 완료하지 못했고, 이번 영상 검증 결과는 합성 입력 기준이다.

## 실행과 외부 서버 모드

기본 실행은 별도 옵션이 필요 없다.

```bash
source ~/colcon_ws/install/setup.bash
ros2 run docking dock_turn_backup
```

시작 로그에서 `Using isolated docking server /stella_docking_.../docking_server`와 전용 action/target 이름을 확인한다. 자동 실행 모드에서 설정의 `dock_action`, `dock_pose_topic`, `tag_refinement_target_pose_topic`은 전용 namespace 아래의 경로로 사용된다. `start_bridge=false`인 경우 외부 검출 토픽은 설정된 원래 경로를 사용한다.

`manage_stack=false` 또는 `start_docking_server=false`이면 자동 namespace 분리를 하지 않는다. 이때 `dock_action`, `tag_refinement_target_pose_topic`, `dock_pose_topic`은 지정한 외부 경로 그대로 사용한다. 새 `docking_server_node` 파라미터(기본 `/docking_server`)로 외부 lifecycle 대상도 지정할 수 있다. 외부 모드 역시 중복 endpoint에는 목표를 보내지 않는다.

실물 로봇의 전체 도킹 성공률과 최종 위치 오차를 측정한 결과는 아니다. 이번 검증은 첨부 로그의 액션 충돌과 인식 프로세스 종료 문제를 대상으로 한다.
## 2026-09-15 후진 중 측벽 충돌과 평면 재획득 실패

최신 실행은 태그 정밀 보정, 180° 회전, LiDAR 후면 평행 정렬까지 완료했다. 후진 2.1초 뒤 휠 전용 yaw는 `+0.01°`였지만 odom은 `+4.14°`, raw IMU 적분은 `+5.25°` 변했다. 그런데 후진 평면 추정은 `-0.68°`에 머물렀고, 기존 루프가 평면이 1° 이내일 때마다 IMU 기준을 다시 설정하여 `imu_heading_drift=0`으로 지웠다. 이 때문에 각속도 명령은 계속 0이었고 측벽 접촉을 막지 못했다.

정지 직후 평면 후보는 `-5.57°`로 변했다. 이는 IMU가 관측한 차체 회전과 부호·크기가 맞지만 기존 `5°` 후보 상한에 걸려 폐기되었고, 2초 뒤 재획득 실패로 종료됐다.

수정 후에는 최초 정지 평면의 `plane_error + robot_yaw`를 고정한다. 필터의 큰 점프는 정지 상태에서 새로 획득할 수 있고, 8°까지의 유효 평면은 3° 이상이면 제자리 저속 정렬 후 후진을 재개한다. 후진 속도는 0.035 m/s로 낮추고 두 평행 가이드 레일이 검출되면 중앙 오프셋도 경로 보정에 사용한다.

## 2026-09-17 정상 후진의 IMU 바이어스 오판

로봇은 정밀 진입과 평행 정렬을 마치고 직진 후진했다. 중단 직전 휠 전용 yaw 변화는 `-0.05°`, LiDAR 평면의 기준 대비 변화는 약 `+0.65°`여서 물리적으로 서로 일치했다. 반면 IMU 적분은 `+1.52°`, IMU 보정 odom은 약 `+1.44°` 변했다. 기존 판정은 IMU와 odom을 독립된 두 증거로 잘못 취급하여 각각 계산된 `+2.17°`, `+2.09°` 잔차가 2°를 넘자 정상 평면을 거부했다. 정지 후에도 같은 센서 바이어스가 남아 `motion_inconsistent` 재획득 제한 3초를 소진했다.

odom yaw가 같은 IMU에 의해 보정된다는 상관관계를 판정에 반영했다. 이제 `LiDAR + 엔코더 전용 yaw`가 일치하면 IMU 계열의 동반 바이어스로 중단하지 않는다. 반대로 바퀴가 미끄러져 엔코더가 회전을 놓쳐도 `LiDAR + IMU 계열`이 일치하면 실제 평면을 받아들인다. 두 그룹과 모두 모순되는 RANSAC 평면만 거부한다. 최신 로그의 세 잔차와 전체 후진 루프를 재현하는 회귀 시험을 추가했다.
